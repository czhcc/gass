# AGENTS.md

## 1. 项目技术栈

本项目采用以下技术栈：

- Java 21
- Spring Boot
- Maven
- Lombok
- Spring Data JPA（如果项目使用）
- Flyway（如果项目使用）

所有新增代码必须兼容项目实际使用的依赖版本。

禁止擅自升级 Java、Spring Boot 或其他依赖版本。

## 2. Java 代码格式规范

### 2.1 基本格式

- 使用 UTF-8 编码。
- 使用 4 个空格作为基础缩进单位。
- 禁止使用 Tab 缩进。
- 建议每行不超过 120 个字符。
- 使用 Unix 风格换行符 LF。
- 文件末尾保留一个换行符。
- 删除行尾多余空格。
- 大括号采用 K&R 风格，左大括号不单独换行。
- if、for、while 等控制结构必须使用大括号。
- 不允许无意义的连续空行。
- Java 文件的最终格式以 Spotless 配置为准。

### 2.2 Java 格式化器

本项目使用：

- Spotless Maven Plugin
- Palantir Java Format
- PALANTIR 格式风格

禁止使用 Google Java Format 的 GOOGLE 风格，
避免将代码转换为 2 空格缩进。

不允许手工修改已格式化代码来对抗格式化器。

### 2.3 import 规范

- 禁止使用通配符 import。
- 删除未使用的 import。
- 不使用没有必要的完全限定类名。
- import 排序以 Spotless 配置为准。

### 2.4 命名规范

- 类和接口：PascalCase
- 方法和变量：camelCase
- 常量：UPPER_SNAKE_CASE
- 包名：全部小写
- 枚举类型：PascalCase
- 枚举常量：UPPER_SNAKE_CASE

禁止使用无意义的名称，例如：

- data1
- temp2
- obj
- list1

允许在很短的局部作用域内使用常见变量名称。

## 3. Java 编码规范

### 3.1 类设计

- 遵循单一职责原则。
- 优先保持现有架构。
- 不新增不必要的抽象层。
- 不为简单功能创建复杂的设计模式。
- 不在 Controller 中编写复杂业务逻辑。
- 不在 Repository 中编写业务流程。

### 3.2 方法设计

- 方法应尽量只负责一项明确的工作。
- 避免过深的条件嵌套。
- 优先使用提前返回减少嵌套。
- 避免重复代码。
- 不捕获异常后直接忽略。
- 不随意使用 RuntimeException 代替业务异常。
- 不随意引入 Optional、Stream 或反射。

### 3.3 注释规范

- 对外公开 API 应有必要的 Javadoc。
- 复杂业务逻辑应有说明。
- 注释解释原因、约束和业务规则，而非重复代码。
- 新增业务注释优先使用中文。
- 不删除仍然有效的历史注释。
- 不生成无意义的模板注释。

## 4. Spring Boot 开发规范

### 4.1 分层

遵循项目现有分层方式：

- Controller：HTTP 接口和参数校验
- Service：业务逻辑
- Repository：数据访问
- DTO：接口输入输出
- Entity：持久化对象
- Config：配置
- Exception：异常处理

不强制重构已有包结构。

### 4.2 依赖注入

统一使用构造器注入。

禁止使用字段级 @Autowired。

已有 Lombok 约定时，可以使用：

@RequiredArgsConstructor

依赖字段使用 private final。

### 4.3 API 设计

- 保持已有 API 路径和响应格式。
- 使用 Jakarta Validation 进行参数校验。
- 优先使用项目已有的统一异常处理机制。
- 不直接暴露 JPA Entity，除非项目明确采用这种设计。
- 不将敏感信息写入日志。

### 4.4 事务管理

- 根据业务需要使用 @Transactional。
- 不随意扩大事务范围。
- 注意 Spring 代理与内部方法调用问题。
- 修改数据时保持原有事务语义。

### 4.5 Lombok

- 使用项目已有的 Lombok 风格。
- 优先使用 @Getter、@Setter、@RequiredArgsConstructor。
- 避免在 JPA Entity 上直接使用 @Data。
- 不无故引入 @SneakyThrows。

## 5. 数据库规范

- 使用项目现有的数据访问方式。
- 不随意修改表结构。
- 需要修改数据库结构时，优先使用 Flyway。
- 不修改已经执行过的历史迁移脚本。
- 数据库字段映射遵循现有命名约定。

## 6. 代码修改原则

### 6.1 最小改动

执行任何任务时：

1. 先阅读相关代码。
2. 理解当前实现及调用关系。
3. 只修改完成任务必需的文件。
4. 不进行无关重构。
5. 不修改无关接口。
6. 不随意引入新依赖。
7. 不删除现有测试。

### 6.2 兼容性

除非任务明确要求：

- 不改变已有 API 行为。
- 不改变数据库字段含义。
- 不改变公共方法签名。
- 不改变已有异常语义。
- 不破坏现有数据兼容性。

### 6.3 新增代码

- 遵循已有包结构。
- 优先复用已有类和工具。
- 不创建功能重复的工具类。
- 不添加未使用的代码。
- 对必要的业务逻辑添加测试。

## 7. Java 格式化范围与验证

### 7.1 作用范围

本规范仅适用于当前 Maven 模块及其子目录。

- 仅格式化当前模块中的 Java 文件。
- 不格式化其他 Maven 模块。
- 不修改其他模块的代码格式。
- 不因格式规范而重构其他模块。

### 7.2 Spotless 执行

在当前模块目录执行：

    mvn spotless:apply
    mvn spotless:check

### 7.3 跨模块修改

如果任务需要修改其他 Maven 模块：

- 允许按业务需要修改其他模块。
- 遵循目标模块自身的编码规范。
- 不将当前模块的格式规范强制应用到其他模块。
- 不执行父项目级 spotless:apply。
- 不进行无关的全项目格式化。

### 7.4 验证

执行格式化后：

1. 检查当前模块格式。
2. 编译受影响模块。
3. 运行相关测试。
4. 检查 git diff。
5. 确认没有无关格式修改。

## 8. Git 修改规范

- 不提交 target/ 等构建产物。
- 不进行与当前任务无关的全项目格式化。
- 不覆盖用户尚未提交的修改。
- 不执行破坏性的 Git 操作。
- 修改完成后检查 git diff。
- 首次引入 Spotless 时，
  将格式基线调整与业务功能变更分开提交。

## 9. Codex 工作流程

处理开发任务时遵循：

1. 分析需求。
2. 阅读相关类和配置。
3. 确定最小修改范围。
4. 添加或更新相关测试。
5. 实现功能。
6. 执行 Spotless 格式化。
7. 检查格式、编译及相关测试。
8. 检查 Git diff。
9. 输出修改说明和验证结果。

## 10. 任务完成输出

完成任务后，简要说明：

- 修改了哪些文件。
- 实现了什么功能。
- 是否执行了 Spotless。
- 编译和测试是否通过。
- 是否存在尚未解决的问题。

不得虚构未执行的测试或检查结果。
