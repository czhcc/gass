# 场景效果判定

本文汇总关于推演轮数、图谱传播范围和业务效果判定的讨论，以最后确认的需求为准：**在场景指定的步数结束后评估目标效果，达到目标则判定业务成功，未达到目标则判定业务失败。**

本文包含当前实现的说明、已查询运行的分析，以及拟议设计。业务效果判定机制尚未实现；下文的规则字段、表达式上下文和结果结构均为设计示意。

## 1. 核心目标

场景需要明确“在多少步后，达到什么效果”。系统据此回答：

- 是否在约定的评估时点达到业务目标？
- 哪些指标达标，哪些未达标？
- 实际结果与目标相差多少？
- 如果未能完成评估，是模型故障、用户停止，还是资源预算提前耗尽？

本次需求不要求推演达到一个所有对象、所有行动都处理完的“完美结束状态”。是否需要全量审查、关闭哪些通道、允许保留多少风险，由场景目标决定。

此前讨论的“初始潜在影响对象全部审查、可控通道处置完成、无待处理事件”可以作为某个场景的一组目标，但不应成为所有泄密场景或所有领域场景的固定成功标准。

## 2. 轮数、Action 和图谱距离

当前系统的一轮，是按场景配置的顺序，让尚未结束且未耗尽决策预算的 Agent，各进行至多一次决策。后面的 Agent 可以看到前面 Agent 执行后的最新状态。

- “计算单步”推进一轮。
- “继续计算”自动逐轮推进。
- 一轮可以产生多个 Action 和多条事件。
- 对象在界面上画得远近，不影响轮数；相关的是图谱路径经过的关系数量。

目前泄密演示的单次 `SIMULATE_PROPAGATION` 沿一条启用的直接关系，让一个目标对象模拟接收信息。演示只有一个传播 Agent，因此一轮最多由该 Agent 执行一次此类传播。

例如 `文档 → A → B → C`，在通道始终开放、每轮都沿该路径传播的前提下，通常至少需要三次成功传播，才能到达 C。分支路径会消耗额外传播次数；分析、拒绝、权限限制和通道处置也会影响传播进度。多个传播 Agent 顺序执行时，同一轮可能推进多跳，因此不存在固定的“一轮等于一层关系”。

轮数较少可能截断传播，但增加轮数也不保证覆盖全部对象。还需考虑 Agent 的目标、权限、可见范围和其他预算。没有传播 Agent 或传播权限的场景，不会因增加轮数而自动模拟传播。

## 3. 当前实现与限制

| 项目 | 当前行为 |
| --- | --- |
| 最大轮数 | 场景配置和演示创建页面均可填写 1～20 的整数 |
| 表单默认值 | 普通场景默认显示 5 轮，演示默认显示 8 轮，均可调整 |
| 配置保存 | 演示请求显式提交 `maxSteps`；场景和运行保存所选上限 |
| Agent 决策预算 | 默认创建的 Agent 最多各决策 10 次 |
| 全局预算 | 默认最多 50 次 Agent 决策，另有事件、模型请求、Token、状态变更和实际计算耗时预算 |
| 暂停等待 | 不计入实际推演耗时 |
| 当前完成判定 | 所有 Agent 均提交并被接受的 `END`，才标记 `COMPLETED` |
| 当前轮数耗尽 | 达到 `maxSteps` 时标记 `BUDGET_EXHAUSTED`，原因 `MAX_STEPS` |

`END` 表示 Agent 自报结束。现有引擎没有进一步校验审查覆盖率、通道处置效果等业务目标。

只读分析 Action 可以被重复执行，不会自动把对象标记为已审查，也不会自动结束任务。因此，单靠 Agent 选择 `END` 或提高最大轮数，不能可靠判断业务效果。

- 最大轮数为 6，实际执行 6 轮。
- 12 次 Agent 决策全部被接受，没有 Action 拒绝，没有 Agent 提交 `END`。

| 2 | 分析文件 F | 禁用系统 S → T 的同步 |
| 3 | 分析人员 A | 审查人员 A |

| 5 | 分析人员 C | 审查人员 C |

- 已关闭 `share_ac` 和 `sync_st` 两条可控通道，结果为模拟处置。
- 文件 F、人员 A/B/C、系统 S 已审查，共 5 个对象。

- 没有待处理的注入事件。
- 未执行传播 Action；这些结果不能用于证明真实泄密发生或真实泄密已被阻止。

同一结果在不同目标下可以得到不同结论：

| 假设配置的目标 | 对该运行的业务评价 |
| --- | --- |
| 第 6 轮结束时，关闭两条指定通道，并审查文件 F、人员 A/B、系统 S | 成功，目标均已达到 |

以上目标仅用于说明判定方式，并未写入该运行的原始配置。不能把事后选择的目标当作该运行已经配置的成功标准。

## 5. 拟议判定流程

### 5.1 在场景中定义评估时点和目标

场景保存以下内容：

1. **评估步数**：例如第 6 轮结束。当前“单步”对应一轮，应在界面中统一说明计数单位。
2. **目标范围**：需要检查的对象、关系、请求或事件。
3. **目标条件**：指标、阈值或状态表达式。
4. **条件组合**：例如全部条件满足才成功。

本次讨论以“指定轮数结束后统一评估”为基准。某一轮提前达标后是否立即结束，需要另行明确，不能默认提前成功；后续状态变化可能使目标重新不满足。

### 5.2 到达评估时点后给出业务结果

- 完成指定轮数后，由执行引擎读取可信状态并计算目标指标。
- 按场景保存的规则判断成功或失败。
- 未达到效果时记录未满足条件、实际值、目标值和相关对象。
- 达到约定评估轮数，应触发业务效果判定，不能只显示“预算耗尽”。

在启用这套机制的场景中，Agent 提交 `END` 仍表示该 Agent 停止工作，不能替代业务效果判定。全部 Agent 提前结束时，也不能据此自动宣告业务成功；提前结束与指定时点评估的衔接需要在实现中明确处理。

### 5.3 分开记录执行结束原因与业务评价

| 维度 | 示例 |
| --- | --- |
| 执行结束原因 | 达到约定评估轮数、模型调用失败、用户停止、其他资源预算耗尽 |
| 业务效果 | 成功、失败、尚未完成评估 |
| 评价依据 | 目标定义、实际指标、阈值、未满足条件、评估时的状态版本 |

例如“达到第 6 轮，业务目标未达标”是一次正常执行到评估时点后的业务失败。模型故障导致只执行 3 轮，则应记录中断和未完成评估，不能直接等同于“第 6 轮仍未达到目标”。

业务评估步数与资源保护预算是不同概念。其他预算提前耗尽时，需要解释为何没有执行到评估时点。已有运行没有保存业务规则时，不应事后自动改写原始评价。

## 6. 通用规则设计

固定在引擎中的职责包括：加载规则、校验表达式、提供可信上下文、计算指标、组合条件、记录评价结果。每个场景保存具体业务条件，无须逐个增加专用的 Java 完成判断分支。

可沿用现有 CEL + 声明式 Action 的设计方向，为场景增加声明式效果规则。以下仅为结构示意，不是现有 API：

```json
{
  "evaluation": {
    "atRound": 6,
    "mode": "ALL",
    "conditions": [
      {
        "id": "channels_handled",
        "description": "两条指定通道均已关闭",
        "expression": "metrics.remainingRequiredChannels == 0"
      },
      {
        "id": "key_objects_reviewed",
        "description": "四个关键对象均已审查",
        "expression": "metrics.reviewedKeyObjects == 4"
      }
    ]
  }
}
```

引擎应提供初始状态、当前状态、固定的目标集合、可信指标和事件统计。规则只读取这些数据进行判断，不应修改世界、调用模型或访问外部服务。

多跳可达范围由图查询组件计算，CEL 组合条件和阈值。如果目标采用“初始潜在影响范围”，应依据运行的初始图谱和指定来源计算并固定集合；不能在关闭关系后缩小待审查集合。图查询的起点、关系类型、方向及深度也应明确。

| 场景 | 可配置的效果目标示例 |
| --- | --- |
| 泄密调查与处置 | 指定轮数内的审查覆盖率、指定通道关闭率、关键对象状态 |
| 银行转账模拟 | 指定请求的处理结果、资金守恒、待处理请求数量 |
| 审批流程 | 截止步数的审批通过率、未处理待办数量 |
| 对象状态迁移 | 指定对象到达目标状态的数量或比例 |

使用已有状态、查询和指标的新场景，可以只增加配置。需要全新数据或计算能力时，再扩展引擎提供的通用能力。规则、目标集合及其版本应随运行冻结，保证评价可复核，并在分支中明确继承方式。

## 7. 结果展示与后续实现边界

界面应同时展示执行结束原因和业务结果。例如：

> 已执行 6/6 轮；业务目标未达标。审查覆盖率实际为 71.4%，要求至少 80%；两条指定通道均已关闭。

评价详情应列出各条件的目标与实际值，以及未满足条件涉及的对象、关系或事件。这样可以判断失败原因，而不必仅通过事件日志推测。

后续实现需要完成：场景规则维护、规则与指标校验、评估时点处理、结果持久化、界面展示及历史兼容。还需明确全部 Agent 提前结束时的处理方式，以及分支继承或重新开始评估步数的规则。本次仅整理讨论内容，不包含上述功能的代码改造。
